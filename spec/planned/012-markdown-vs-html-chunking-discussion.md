# Spec 012: Markdown vs HTML 文档格式切分讨论

> 创建日期：2026-06-20
> 状态：**planned**（讨论阶段）
> 核心问题：**文档源格式用 Markdown 还是 HTML 更利于清洗切分？**

---

## 1. 当前文档画像（实测数据）

对 110 篇 Raw 文档的统计：

| 特征 | 数量 | 说明 |
|------|------|------|
| 总文档数 | 110 篇 | 全部 `.md` 格式 |
| 总行数 | 11,744 行 | 平均 ~107 行/篇 |
| 表格行 | 5,241 行 | 占总行数 44.6%，**高度表格化** |
| wikiLinks | 7,619 个 | 平均 ~69 个/篇，**极高密度** |
| 代码块 | 18 个 | 仅 6 篇文档有代码块，极少 |
| HTML 标签 | 67 个 | 全部是 `<br>`，无复杂 HTML |
| 合并单元格 | 0 | 无 `colspan`/`rowspan` |
| `#` 标题 | 111 个 | 每篇约 1 个（文档标题） |
| `##` 标题 | 979 个 | 每篇约 9 个（主要章节） |
| `###` 标题 | 600 个 | 每篇约 5 个（子章节） |

**关键特征**：
- **纯 Markdown**，几乎无 HTML 混用（仅 67 个 `<br>`）
- **表格密集**，近半数行是表格行
- **wikiLinks 极密**，是信息组织的主要方式
- **标题层级清晰**，`##` 是主分块边界
- **无合并单元格**，表格结构简单

## 2. 两种格式的切分难度对比

### 2.1 Markdown 表格（当前方案）

```markdown
| 序号 | 名称 | 金额 |
|------|------|------|
| 1    | 项目A | 100  |
| 合计 | -    | 100  |
```

**识别**：`|` 开头 + `|` 结尾 → `isTableLine()`
**切分**：表格作为一个不可分割单元，整体保留

**优势**：
- 行级识别，O(n) 复杂度
- 不需要解析器，两个字符串判断搞定
- 表格边界天然清晰（空行分隔）
- 与 wikiLinks `[[xxx]]` 语法零冲突

**劣势**：
- 表格内不能有空行（否则被切断——已修复，靠前瞻检测）
- 不支持合并单元格（当前文档也不需要）
- 嵌套表格不支持（当前文档也没有）

### 2.2 HTML 表格

```html
<table>
  <thead>
    <tr><th>序号</th><th>名称</th><th>金额</th></tr>
  </thead>
  <tbody>
    <tr><td>1</td><td>项目A</td><td>100</td></tr>
    <tr><td>合计</td><td>-</td><td>100</td></tr>
  </tbody>
</table>
```

**识别**：需要 HTML 解析器（正则不可靠）
**切分**：需要解析 DOM 树，提取 `<table>` 节点

**优势**：
- 结构严格，`<table>` 到 `</table>` 是明确的边界
- 支持合并单元格 `colspan`/`rowspan`
- 支持嵌套表格
- 嵌套格式（粗体、链接）在 HTML 中是标签，不影响表格行识别

**劣势**：
- **需要 HTML 解析器**（cheerio/jsdom），增加依赖
- 解析复杂度远高于 Markdown 行级判断
- HTML 标签本身占大量字符，降低有效信息密度
- 与 wikiLinks 语法不兼容，需要转义或改用 `<a>` 标签

---

## 3. 核心对比

| 维度 | Markdown | HTML |
|------|:---:|:---:|
| **表格识别** | `startsWith('|')` ✅ 极简 | 需 DOM 解析 ❌ |
| **切分速度** | O(n) 行扫描 | O(n) 但常数大（解析树） |
| **表格边界** | 空行分隔（需前瞻） | `<table>...</table>` 明确 |
| **合并单元格** | ❌ 不支持 | ✅ 支持 |
| **嵌套表格** | ❌ 不支持 | ✅ 支持 |
| **wikiLinks 兼容** | ✅ `[[xxx]]` 原生 | ❌ 需改为 `<a>` |
| **信息密度** | 高（无冗余标签） | 低（标签占 30%+ 字符） |
| **人类可读性** | ✅ 高 | ❌ 低 |
| **新依赖** | 0 | cheerio/jsdom |
| **当前文档适配** | ✅ 完美匹配 | 过度设计 |

---

## 4. 结论：Markdown 远优于 HTML

### 4.1 当前文档不需要 HTML

| HTML 优势能力 | 当前文档是否需要 |
|--------------|:---:|
| 合并单元格 | ❌ 0 个 |
| 嵌套表格 | ❌ 0 个 |
| 复杂 HTML 标签 | ❌ 仅 67 个 `<br>` |
| HTML5 语义标签 | ❌ 0 个 |

**当前文档 100% 是纯 Markdown，没有任何 HTML 表格特征。换成 HTML 是为了解决不存在的问题。**

### 4.2 Markdown 的切分已经验证有效

```
表格被切断率: 29.3% → 0.0% ✅
110 篇文档，5241 行表格，0 切断
```

### 4.3 HTML 会带来实际的负面影响

1. **信息密度下降**：HTML 表格标签约占 30-40% 字符

   ```html
   <tr><td>1</td><td>项目A</td><td>100</td></tr>   ← 48 字符
   ```
   ```markdown
   | 1 | 项目A | 100 |                               ← 20 字符
   ```

   同样的内容，HTML 版本 chunk 会更少、更大，或者需要更多 chunk。

2. **wikiLinks 不兼容**：`[[中信证券]]` 在 HTML 中需要改成 `<a href="wiki/中信证券">中信证券</a>`，或保留 `[[]]` 但混在 HTML 标签中更难提取。

3. **嵌入成本增加**：embedding 输入会包含大量 `<td>`/`<tr>` 标签噪声，降低向量质量。

4. **新依赖**：需要 cheerio（~2MB）或 jsdom（~10MB），与"零新依赖"原则冲突。

### 4.4 唯一值得考虑 HTML 的场景

如果未来文档出现以下情况，才值得考虑 HTML：
- 需要 `colspan`/`rowspan` 合并单元格
- 需要嵌套表格
- 需要富文本格式的表格单元格（表格内有图片、复杂格式）

**当前和可预见的未来都不存在这些需求。**

---

## 5. 推荐策略

### 5.1 保持 Markdown，不做格式迁移

当前 Markdown + 表格感知 chunker 的组合已经将表格切断率降到 0%，没有切分质量问题需要解决。

### 5.2 短期优化方向（不换格式）

| 方向 | 说明 | 优先级 |
|------|------|:---:|
| wikiLinks 密度优化 | 某些段落 wikiLink 密度 > 30%，考虑在 embedding 前选择性去除 | P2 |
| 表格摘要生成 | 大表格（> 2000 字符）生成自然语言摘要供向量检索，原文保留在 chunk 中 | P3 |
| chunk 内表格结构化提取 | 将表格解析为 JSON 结构存入 metadata，供结构化检索使用 | P3 |

### 5.3 如果未来必须支持 HTML 表格

不需要全量迁移为 HTML，而是**在 Markdown 中内嵌 HTML 表格**（Markdown 原生支持）：

```markdown
## 章节

普通段落文字

<table>
  <tr><th>列1</th><th>列2</th></tr>
  <tr><td>值1</td><td>值2</td></tr>
</table>

后续文字
```

chunker 增强：在 `splitParagraphsTableAware` 中增加 HTML 表格识别分支，检测 `<table>` 到 `</table>` 的范围，作为受保护区域。**不需要改变其他文档部分的 Markdown 格式。**

---

## 6. 一句话总结

> 当前文档是高度表格化的纯 Markdown，表格感知 chunker 已将切断率降到 0%。HTML 的优势（合并单元格、嵌套表格）在当前文档中完全用不到，而它的劣势（信息密度低、wikiLinks 不兼容、需新依赖、embedding 噪声）是实打实的。**保持 Markdown，不迁移。**
